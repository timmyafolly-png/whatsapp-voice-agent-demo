## What it does

Sandeep taps **Approve** or **Request information** in his internal email.
Those links hit this scenario's webhook carrying three values:

```
?ref=BR-Q-20261022-1041&token=<the row's approval_token>&action=approve
```

```
1. Webhook           the link is tapped
2. Find the row      Projects sheet, matched on quote_reference
3. Build the fields   greeting, formatted total, total in pence
4. Router
   route 1   expire the previous unpaid payment link
   route 2   approve: create the link, send the quotation, stamp the row, confirm
   route 3   request information: email the customer, save the draft, confirm
```

## Why it is safe by construction

**A wrong token sends nothing.** Every route carries
`token = approval_token` as its first filter condition. Fail it and no module
on any route runs.

**An unknown reference sends nothing.** `filterRows` emits no bundle when
nothing matches, which halts the branch before any email module exists. A
guessed reference cannot produce an email.

**The expiry cannot block the send.** Expiring an old link sits on its own
router route rather than in front of the create step. A filter in the middle
of a chain stops everything after it, which is the bug that bit this project
before, so the two live in parallel. The expire call also carries a `Resume`
handler, because expiring a session that is already paid or expired is an
error we want to ignore rather than a reason to withhold a quotation.

**The amount cannot drift.** The Stripe amount is `total` from the row,
converted to pence in one place, and the email prints the same figure. Neither
is typed twice.

**The India team is not contacted.** There is no India recipient anywhere in
this scenario. Their handover belongs to the payment stage.

## Idempotency

Tapping Approve twice expires the first session and issues a second. The
customer's older link stops working rather than two live links existing. That
is the behaviour Sandeep asked for.

## The two tests

These must run from a machine that can reach `hook.eu1.make.com`. The build
container cannot; its egress proxy blocks it.

**Negative first.** This is the test that matters, because it proves the
guarantee rather than the feature.

```
curl -i "https://hook.eu1.make.com/u6k1ltrlcq5qs82upswhorlyujnkd531\
?ref=BR-Q-20261022-1041&token=wrong&action=approve"
```

**Result, 22 Oct 2026, 22:21 UTC: PASSED.** Execution
`8e5b394da28647e1960c2f22a203c3e9`, SUCCESS, **3 operations**.

Three operations is the proof. It accounts for the webhook, the row lookup and
the variables, and nothing else; routers cost nothing, so every module past
the router was skipped. Had any of them run the count would be five or more,
and the sheet write alone would have added one. So no email left, no Stripe
session was created, and row 2 was not touched.

The response was the bare word `Accepted`, which is Make's own default. That
is correct: the response modules sit on the routes too, so none of them ran
either. A styled page here would have meant the token check let the request
through.

**Then the positive.**

```
curl -i "https://hook.eu1.make.com/u6k1ltrlcq5qs82upswhorlyujnkd531\
```

**Result, 22 Oct 2026, 22:43 UTC: PASSED.** Execution
`a790ebdc66634bbcacf1d2899a55811d`, SUCCESS, **7 operations**: webhook, row
lookup, variables, Stripe session, quotation email, row update, response. The
expire route correctly skipped, since this row had no earlier session.

The HTML confirmation page came back and the quotation rendered with the logo,
the greeting, both fee lines, the combined discount, the conditions block, the
turnaround and the payment button.

It took three attempts to get there. The first two failed with
BundleValidationError at five operations, and the cause was `sender` in
email:ActionSendEmail v6 being `"type": "email"` while it had been set to the
display name `BuildRegs`. `validate_module_configuration` accepts that,
because it does not enforce the format, so checking the module in isolation
passed while every run failed. The display name belongs in `from`.

One defect the first successful run exposed: every money figure rendered in
European format, `1.248,50` rather than `1,248.50`. Make's `formatNumber`
falls back to the organisation's locale when separators are omitted, and this
organisation's is European. All six calls in the quotation email and the
`totalFmt` variable now pass `"."` and `","` explicitly. **Never call
`formatNumber` here without separators.**

**Then run the positive a second time.** The first session should be expired
and a new one issued, which is the duplicate-click behaviour Sandeep asked
for. Confirm in Stripe that the first session shows as expired.

## Known limits

- Up to **four** project types render as itemised fee lines. The price list
  holds eight types; combining more than four at one property is not a real
  case, and the cap keeps the fee table buildable without an iterator.
- A bad token or unknown reference gives the browser a generic error rather
  than a friendly page, because the lookup halts before any response module.
  It fails closed, which is the important half.
