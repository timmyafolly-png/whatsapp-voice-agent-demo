## What it does

Sandeep taps **Approve** or **Request information** in his internal email.
Those links hit this scenario's webhook carrying three values:

```
?ref=BR-Q-20261022-1041&token=<the row's approval_token>&action=approve
```

```
1. Webhook           the link is tapped
2. Find the row      Projects sheet, matched on quote_reference
3. Build the fields   greeting, formatted total, total in pence
4. Router
   route 1   expire the previous unpaid payment link
   route 2   approve: create the link, send the quotation, stamp the row, confirm
   route 3   request information: email the customer, save the draft, confirm
```

## Why it is safe by construction

**A wrong token sends nothing.** Every route carries
`token = approval_token` as its first filter condition. Fail it and no module
on any route runs.

**An unknown reference sends nothing.** `filterRows` emits no bundle when
nothing matches, which halts the branch before any email module exists. A
guessed reference cannot produce an email.

**The expiry cannot block the send.** Expiring an old link sits on its own
router route rather than in front of the create step. A filter in the middle
of a chain stops everything after it, which is the bug that bit this project
before, so the two live in parallel. The expire call also carries a `Resume`
handler, because expiring a session that is already paid or expired is an
error we want to ignore rather than a reason to withhold a quotation.

**The amount cannot drift.** The Stripe amount is `total` from the row,
converted to pence in one place, and the email prints the same figure. Neither
is typed twice.

**The India team is not contacted.** There is no India recipient anywhere in
this scenario. Their handover belongs to the payment stage.

## Idempotency

Tapping Approve twice expires the first session and issues a second. The
customer's older link stops working rather than two live links existing. That
is the behaviour Sandeep asked for.

## Before the first test

**The example row in the Projects sheet carries `jamespf1@gmail.com`, a real
customer.** Approving against `BR-Q-20261022-1041` would send James
Pryer-Freeman a real quotation. Change that row's `customer_email` to
`collsdigital@gmail.com`, or add a separate test row, before testing.

Then, with the hook URL from the created scenario:

```
curl "https://hook.eu1.make.com/<hook>?ref=BR-Q-20261022-1041\
&token=EXAMPLE-token-do-not-reuse&action=approve"
```

Expect: a confirmation page in the response, a quotation in the inbox with the
two fee lines and the combined discount, Stripe test mode showing a new
session, and the row moving to `Quote sent` with `approved_at`,
`quote_sent_at` and `stripe_session_id` filled in.

Then the negative test, which matters more:

```
curl "https://hook.eu1.make.com/<hook>?ref=BR-Q-20261022-1041\
&token=wrong&action=approve"
```

Expect: nothing sent, nothing created, no change to the row.

## Known limits

- Up to **four** project types render as itemised fee lines. The price list
  holds eight types; combining more than four at one property is not a real
  case, and the cap keeps the fee table buildable without an iterator.
- A bad token or unknown reference gives the browser a generic error rather
  than a friendly page, because the lookup halts before any response module.
  It fails closed, which is the important half.
