## What it does

The review page posts a prepared quote here. Twelve modules:

```
1 webhook
2 read the four project-type slots
3 subtotal, count, lowest price, the two CSV fields
4 discount, quotation reference, approval token, stamp
5 total and status
6 format the money
7 ROUTER
    8a  no reference supplied  -> append a new project row
    8b  reference supplied     -> find the row, update it in place
    8c  action = submit        -> email Sandeep the preview with the links
    8d  always                 -> answer the page
```

**Saving sends nothing.** The only email module on this scenario is addressed
to `support@buildregs.co.uk`, so no path here can reach a customer, and that
one is gated on `action = submit`. A save writes the row and stops.

**The approval links** in Sandeep's email point at Phase 2b carrying the
reference and the token this scenario generated, so the two halves meet at the
project row.

## The arithmetic

Make computes the total, not the form. `subtotal - discount + adjustment`,
written once to column S, and Phase 2b reads it from there for both the
quotation and the Stripe amount. Nothing is typed twice anywhere in the chain.

**The combined discount:** 50% off the single lowest-priced selected type,
applied once, only when two or more types are selected. An override from the
review page replaces it, zero included, and the row records that it was
overridden.

**Four slots.** Up to four project types per quote. The price list holds eight,
and combining more than four at one property is not a real case.

## Two things worth knowing

**Variables are split across five modules on purpose.** Sibling variables in a
single SetVariables module cannot reference each other, so the arithmetic runs
in dependency order: slots, then sums, then discount, then total, then
formatting.

**Unit prices come from the form, not the price list.** The review page has to
show Sandeep live prices as he taps, so it holds them, and it sends them here.
Make does every calculation on top of them. The trade-off is that a price
changed in the sheet must also be changed on the form. A small sync job
removes that later; it is not worth blocking launch for.

## The contract the review page must post

| Field | Notes |
|---|---|
| `action` | `save` or `submit`. Anything else is treated as `save` |
| `quote_reference` | empty for a new quote, present when editing a draft |
| `project_reference` | from the original enquiry |
| `customer_name`, `customer_email`, `customer_phone`, `property_address` | |
| `package` | Full or Structural-only |
| `type1`–`type4`, `price1`–`price4` | paired; an empty type ignores its price |
| `adjustment_amount`, `adjustment_reason` | negative amounts reduce the fee |
| `discount_override` | optional; empty means apply the standard rule |
| `approved_scope`, `approved_exclusions`, `next_steps` | |
| `india_notes` | private; shown to Sandeep, held back from the team until payment |
| `turnaround_days` | |

`Draft` and **no email at all**. That is the test that matters, because the
client asked specifically that saving must never send.
